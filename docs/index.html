TechMap 세션 자료

Create ML 사운드 분류, 파라미터부터 온디바이스 추론까지

오디오 분류 모델의 학습 파라미터가 실제 앱의 동작을 어떻게 결정하는지 정리한 실습 문서입니다. 값은 모두 Xcode 26.0 SDK에서 직접 확인했고, 슬라이더를 움직여 결과를 눈으로 확인하실 수 있습니다.

지금 이 파형이 0.975초 단위로 잘려 특징이 되고, 그 특징만 분류기에 들어갑니다. 이 문서의 전부가 그 한 문장입니다.

Xcode 26.0 Create ML MLSoundClassifier SoundAnalysis iOS 15+ 데모 SoundHook (SwiftUI)

개요

이 문서는 세션 산출물 세 가지의 기준 문서입니다. 키노트는 개념과 의사결정을, 이 문서는 재현 가능한 절차를, 데모 앱 SoundHook은 파라미터 변화의 체감을 각각 담당합니다. 세 산출물은 같은 파라미터 집합을 공유하므로, 여기서 조정한 값이 곧 앱의 슬라이더입니다.

학습 없이 시작

Apple 내장 분류기로 파이프라인을 먼저 완성합니다. 코드 한 줄이면 303종을 알아듣습니다.

파라미터 이해

템플릿 기본값이 어떤 가정 위에 서 있는지 확인합니다. 외울 값은 네 개뿐입니다.

교체 가능한 구조

내장 분류기 자리에 직접 학습한 .mlmodel을 넣습니다. 바뀌는 코드는 한 줄입니다.

소리를 읽는 법

사운드 분류는 파형을 그대로 분류하지 않습니다. 고정 길이 구간으로 자른 뒤 특징 벡터를 뽑고, 그 벡터를 분류기에 넣는 전이 학습 구조입니다. 아래 애니메이션이 그 과정입니다.

윈도가 오디오를 훑고 지나가면 오른쪽에 특징이 하나씩 쌓입니다. 학습은 이 특징만 봅니다.

숫자로 보면 이렇습니다

모델이 한 번에 보는 양은 생각보다 작습니다. 아래 막대는 두 숫자의 실제 비율입니다.

한 번에 보는 오디오의 양 비율 509 대 1
3분짜리 노래7,938,000
모델의 한 입15,600

44,100 Hz로 녹음한 3분 곡의 샘플 수와, 16,000 Hz로 변환한 0.975초 한 덩어리의 샘플 수입니다. 뒤의 숫자가 특징 벡터 하나가 됩니다.

직접 확인한 값입니다

아주 작은 데이터셋으로 실제 학습시켜 만든 .mlmodel을 열어 보면 입력이 audioSamples [15600], 메타데이터가 sampleRate 16000입니다. 16,000 × 0.975 = 15,600으로, 특징 추출 윈도와 정확히 일치합니다.

네 칸으로 보는 전체 구조

단계를 눌러 보시면 각 칸에서 무슨 일이 일어나는지 보실 수 있습니다.

학습 없이 시작하기

Apple은 학습 없이 바로 쓸 수 있는 범용 사운드 분류기를 SoundAnalysis에 내장해 두었습니다. 모델 파일을 번들에 넣을 필요가 없고, 초기화 한 줄이면 303종을 구분합니다.

범위를 벗어난 값

제약을 벗어난 windowDuration을 넣으면 오류가 아니라 가장 가까운 지원 값으로 자동 조정됩니다. 설정한 값이 그대로 적용됐다고 가정하지 마시고 다시 읽어 확인하세요.

데이터 준비

직접 학습할 때는 클래스 이름을 폴더명으로 쓰는 구조가 가장 간단합니다. background 폴더를 반드시 넣으세요. 모델에게 "그 외"라는 선택지를 준 적이 없으면, 모델은 침묵조차 아는 소리 중 하나로 우깁니다.

폴더 이름이 곧 정답 라벨입니다
SoundData/
├── clap/         2분 12초
├── knock/        2분 40초
├── whistle/      1분 55초
└── background/   그 외 아무 소리   // 이 줄이 없으면 오탐이 폭증합니다

얼마나 모아야 할까요

녹음 길이를 옮겨 보시면 학습에 실제로 쓰이는 조각 수가 바로 나옵니다. 1분만 녹음해도 조각은 100개가 넘습니다.

템플릿 파라미터

Create ML 사운드 분류 템플릿의 기본값은 MLSoundClassifier.ModelParameters()가 정합니다. 실무에서 손대는 값은 사실상 네 개입니다.

파라미터기본값언제 바꾸나요
featureExtractionTimeWindowSize0.975초짧은 타격음은 줄이고, 문맥이 필요한 소리는 늘립니다
overlapFactor0.5조각을 더 촘촘히 만들고 싶을 때 올립니다
maxIterations25학습 정확도가 계속 오르는 중이면 올립니다
validation.split(strategy: .automatic)검증 세트를 따로 두었다면 고정합니다
algorithm.transferLearning(...)거의 바꾸지 않습니다. 기본이 최선입니다

algorithm의 기본값은 .audioFeaturePrint(type: .sound, revision: 1)와 .logisticRegressor 조합입니다. 앞쪽 특징 추출기는 Apple이 미리 학습해 둔 부분이라 건드릴 일이 없고, 실제로 학습되는 것은 뒤쪽 분류기 한 층뿐입니다. 데이터가 적어도 모델이 나오는 이유가 여기에 있습니다.

기본값을 그대로 쓰되 명시적으로 적어 둡니다
let parameters = MLSoundClassifier.ModelParameters(
    validation: .split(strategy: .automatic),
    maxIterations: 25,
    overlapFactor: 0.5,
    featureExtractionTimeWindowSize: 0.975)

윈도, 오버랩 튜닝

결과가 나오는 간격은 두 값의 곱으로 정해집니다. hop = windowDuration × (1 − overlapFactor). 슬라이더를 움직여 10초 오디오가 몇 개의 윈도로 잘리는지 확인해 보세요.

분석 윈도 시뮬레이터

윈도를 줄입니다

박수, 노크, 유리 깨짐처럼 짧은 소리입니다. 0.5초에서 1.0초 사이를 씁니다. 긴 윈도 안에서는 배경에 묻힙니다.

윈도를 늘립니다

음악, 기계음, 환경음처럼 이어지는 소리입니다. 3.0초에서 5.0초 사이를 씁니다. 넓게 들어야 구분됩니다.

겹침의 상한

overlapFactor 0.5는 모든 소리가 최소 한 윈도의 중앙 부근에 놓이도록 보장하는 최솟값입니다. 그 이상은 연산량만 선형으로 늘고 얻는 것은 급격히 줄어듭니다.

흔들림 잡기

모델 출력을 그대로 화면에 내보내면 라벨이 심하게 떨립니다. 신뢰도 임계값과 연속 판정, 두 가지를 같이 걸어야 실전 품질이 나옵니다. 아래에서 값을 바꿔 보시면 같은 입력이 어떻게 다르게 확정되는지 보실 수 있습니다.

임계값, 연속 판정 시뮬레이터

이 두 줄이 체감 품질을 바꿉니다
guard classification.confidence >= threshold else { streak = 0; return false }
streak = (classification.identifier == last) ? streak + 1 : 1
return streak >= 2   // 연속 2회 같은 라벨일 때만 확정합니다

앱에 연결하기

학습한 모델과 내장 분류기는 같은 인터페이스를 씁니다. 초기화 방식만 다르고 나머지 코드는 완전히 같으므로, 내장으로 먼저 만들고 나중에 교체하셔도 됩니다. analyze 호출은 오디오 탭 스레드가 아니라 전용 직렬 큐에서 하셔야 입력 버퍼가 밀리지 않습니다.

바뀌는 것은 이 한 줄뿐입니다
// 학습 없이
let request = try SNClassifySoundRequest(classifierIdentifier: .version1)
// 직접 학습한 모델로
let request = try SNClassifySoundRequest(mlModel: MySound().model)

데모 앱 SoundHook

데모 앱은 화면이 두 개입니다. 챌린지 탭은 제시된 소리를 직접 내면 분류기가 판정하는 게임이고, 실험실 탭은 같은 분류기를 파라미터를 바꿔 가며 관찰하는 계기판입니다. 게임에서 실패한 미션을 실험실에서 재현하는 흐름이 시연의 축입니다.

챌린지

8라운드, 라운드당 12초입니다. 미션 하나에 여러 레이블을 인정하므로 웃음은 laughter, giggling, belly_laugh 중 무엇이든 성공입니다.

실험실

windowDuration, overlapFactor, 임계값 슬라이더가 있습니다. 챌린지 난이도도 여기서 조절합니다.

시연 포인트

휘파람이나 손가락 튕기기처럼 짧고 높은 소리는 긴 윈도에서 잘 잡히지 않습니다. 실패 직후 실험실에서 windowDuration을 줄여 다시 시도하시면, 파라미터가 인식 성능을 어떻게 바꾸는지 한 번에 보여 주실 수 있습니다.

배포 체크리스트

  • NSMicrophoneUsageDescription을 사용자 언어로 작성하세요. 누락되면 실행 중 종료됩니다.
  • AVAudioSession 카테고리를 설정하고 인터럽션 알림을 처리하세요.
  • 백그라운드로 전환되면 엔진을 정지하세요. 계속 들어야 한다면 오디오 백그라운드 모드를 신청하셔야 합니다.
  • 온디바이스 모델은 앱 업데이트 주기에 묶입니다. 갱신 계획을 미리 세우세요.
  • 오디오가 기기 밖으로 나가지 않는다는 점을 사용자에게 명시하세요.
  • 내장 분류기의 클래스 목록은 SDK 버전에 따라 달라질 수 있으므로 실행 시점에 조회하세요.
